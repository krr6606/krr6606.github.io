## 무엇을 설명하느냐에 따라 고르기

| 다이어그램 | 답하는 질문 | 프로젝트 문서 섹션 | Mermaid |
|---|---|---|---|
| **클래스** | 무엇으로 이루어져 있는가? (런타임 구조) | 2. 시스템 구조 | `classDiagram` |
| **시퀀스** | 시간 순서로 어떻게 상호작용하는가? | 2·3. 구조/기능 | `sequenceDiagram` |
| **상태(FSM)** | 어떤 상태를 오가는가? | 2·3. 구조/기능 | `stateDiagram-v2` |
| **플로우차트** | 어떤 갈림길을 지나는가? (로직) | 3. 핵심 기능 | `flowchart` |
| **ER** | 데이터가 어떤 필드로 이루어지고 서로 어떻게 이어지는가? | 2·3. 구조/기능 | `erDiagram` |

- 하나의 기능에 5개를 다 넣을 필요는 없습니다. **설명하려는 것**에 맞는 1~2개면 충분합니다.
- 흔한 조합: **클래스로 구조** + **시퀀스로 호출 흐름** + (갈림길이 많은 규칙만) **플로우차트**.

### 소스에서 읽히는 것 → 다이어그램

종류는 제목이나 습관이 아니라 **그 절이 설명하는 것**으로 고릅니다. 문서의 글과 코드(`code/`·문서 코드 블록)에서 아래 신호를 찾습니다.

| 설명하는 것 | 코드의 신호 | 문서 글의 신호 | 다이어그램 |
|---|---|---|---|
| 데이터가 어떤 필드로 이루어지고 서로 어떻게 이어지는가 | 필드만 있거나 거의 필드만 있는 클래스·`struct`(`[Serializable]`·DTO·세이브 클래스), `ScriptableObject` 데이터 자산, CSV·TSV·JSON을 읽어 채우는 클래스, 다른 데이터를 `id`로 가리키는 필드, DB 테이블·키 — **데이터가 둘 이상이고 서로 이어지거나, 글이 표·열 구조를 설명할 때** | "데이터 표", "필드", "열", "TSV·CSV·JSON", "저장", "id로 연결" | **ERD** (데이터 하나의 필드 목록뿐이면 표로 충분) |
| 여러 클래스·함수를 차례로 타고 들어가는 호출 흐름 | 한 메서드 안에서 다른 클래스의 메서드를 부르고, 그 안에서 또 다른 클래스를 부름(`A.Do()` → `B.Run()` → …), `event`·`Action` 구독과 호출, 콜백·`await`, RPC·서버↔클라이언트 메시지 | "~가 ~를 부르고", "요청 → 응답", "보낸다·받는다", 주체가 둘 이상인 순서 | **시퀀스** — 참여자는 클래스(객체)·서버·클라이언트, 화살표는 메서드 호출·메시지 |
| 한 메서드·한 규칙 안의 조건 분기와 검증 단계, 무엇을 고르는가(선택·판정) | 한 메서드 안의 `if`/`else`·조기 `return`·검사 순서, 확률·랜덤으로 고르기 | "~이면 ~, 아니면", "검사", "실패하면", "랜덤으로 고른다" | **플로우차트** |
| 상태와 그 사이의 전이 | 상태 `enum`과 **그 값을 바꾸는 코드(전이)**, 상태 클래스(`IState`·`Enter`/`Exit`), 턴 단계, Animator 상태·트리거. 종류를 나누기만 하는 `enum`(효과 종류·방향·블록 색)은 상태가 아님 | "상태", "단계", "~로 넘어간다", "전이" | **상태** |
| 클래스 사이의 상속·인터페이스 구현, 또는 핵심 협력 관계 | `: Base`, `: IInterface`, `abstract`·`override`, 다른 클래스를 필드로 들고 그 메서드를 부름 | "상속", "구현", "역할 분담", "~가 ~를 가진다" | **클래스** |

- **클래스 vs ERD**: 동작(메서드)을 가진 객체의 관계·상속은 클래스, 필드만 가진 **데이터의 구조**는 ERD입니다. 저장 위치(디스크·DB·메모리)와 상관없습니다 — 메모리에 읽어 둔 데이터 표·`ScriptableObject`도 ERD입니다.
  세이브·서버 데이터가 있는 프로젝트라면 둘 다 보이면 "런타임과 데이터를 모두 이해한다"는 인상을 줍니다.
- **시퀀스 vs 플로우차트**: 주체(클래스·객체·서버/클라이언트)가 둘 이상이고 차례로 부르면 시퀀스, **한 주체 안**의 갈림길이면 플로우차트입니다. 호출 흐름 안에 갈림길이 있으면 시퀀스의 `alt`로 쓰거나, 그 메서드 하나만 플로우차트로 따로 그립니다.
- **플로우차트는 갈림길에** 씁니다: 한 메서드·한 규칙의 분기, 그리고 기획 단위의 **플레이어 행동 흐름·코어 루프**(플레이어가 무엇을 하고 어디로 돌아오는가). 구성 요소 사이의 큰 흐름(입력 → 처리 → 화면)을 한눈에 보이는 개요 그림도 플로우차트(`LR`)로 그릴 수 있지만, 노드가 `클래스.메서드()`이고 **차례**가 요점이면 시퀀스입니다.

### 잘못 고른 그림을 알아보는 신호

| 지금 그림 | 이런 모양이면 | 맞는 종류 |
|---|---|---|
| 플로우차트 | 노드가 데이터(클래스·`ScriptableObject`·CSV 표) 이름이고, 화살표가 차례가 아니라 "가진다·`id`로 가리킨다"이며 갈림길이 없음 — 노드 안에 필드·타입을 줄줄이 적었든, 이름만 잇고 필드는 본문·코드에만 있든 같음 | ERD |
| 플로우차트 | 데이터 **하나**의 필드를 노드 안이나 가지로 늘어놓음(이어지는 다른 데이터 없음) | 표 |
| 플로우차트 | 노드가 `클래스.메서드()`나 클래스 이름이고, 갈림길(마름모) 없이 한 줄로 이어지거나 화살표 라벨이 메서드 호출 | 시퀀스 |
| 플로우차트 | 노드의 과반이 상태 이름이고, 화살표 라벨·마름모가 "어느 상태로 넘어가나"의 전이 조건일 뿐이며 되돌아가는 화살표가 있음 | 상태 |
| 클래스 | 메서드가 하나도 없고 필드만 있는 클래스가 대부분 | ERD |
| 시퀀스 | 참여자가 하나뿐이고 갈림(`alt`)만 있음 | 플로우차트 |
| 상태 | 코드에 상태 `enum`·상태 필드가 없고, 상태 이름이 한 메서드의 검사 단계(조기 `return`)일 뿐 | 플로우차트 |
| 플로우차트 | 인터페이스·부모 클래스에서 구현 클래스들로 점선·화살표가 갈라짐(구현 관계를 흉내 냄) | 클래스 |

- 판정은 **그림이 실제로 보여 주는 것**으로 합니다.
- **개요 그림과 시퀀스 가르기** — 노드가 클래스이고 화살표 라벨이 메서드·이벤트 이름이어도 아래면 **개요 그림(플로우차트 유지)**입니다:
  한 노드에서 화살표가 둘 이상 나가거나 되돌아오는 화살표가 있고(구성 요소 전체를 보임), 절의 요점이 **책임 분담·방향**("한 방향으로만 들어온다", "누가 정하나")일 때.
  노드가 갈라짐 없이 한 줄로만 이어지거나, 제목·본문이 **순서·차례**("~ 순서로 전달된다")를 요점으로 말하면 **시퀀스**입니다.
  두 쪽 신호가 함께 있으면 **절 제목이 말하는 요점**으로 정합니다("누가 무엇을 정하는가" → 개요, "전달 순서" → 시퀀스).
- 이 가르기는 "플로우차트 → 시퀀스" 줄에만 씁니다. 인터페이스·부모에서 구현으로 갈라지는 그림(→ 클래스)과 상태 이름·전이 조건의 그림(→ 상태)은 개요 그림처럼 보여도 그 줄이 먼저입니다.
- **갈림길과 상태 신호가 함께 있을 때**(마름모도 있고, 상태 이름·되돌아오는 화살표도 있음) — **그림의 중심**으로 정합니다.
  그림이 **무엇을 고르는가**(선택·판정 — 확률로 패턴 고르기, 검사 결과로 갈라지기)를 보이려는 것이면 **플로우차트**입니다.
  노드의 과반이 상태 이름이고 마름모는 전이 조건일 뿐이면 **상태**입니다(마름모 대신 전이 화살표의 라벨로 씀).
  대기(`Idle`)로 돌아오는 화살표 하나, 상태 이름 노드 하나만으로는 상태 그림이 되지 않습니다.

### 클래스 다이어그램은 한 그림에 한 목적

- **상속 구조**를 보이는 그림에는 상속·구현 관계(`<|--`, `<|..`)에 있는 클래스만 넣습니다. 그 관계 어디에도 없는 클래스(필드·인자로 참조만 하는 클래스)가 섞이면 상속의 뜻이 흐려집니다 → 빼거나 협력 그림으로 나눕니다.
- 상속·구현 화살표가 그림 관계의 **절반을 넘으면** 상속 구조 그림으로 봅니다.
- **협력 관계**를 보이는 그림에는 핵심 클래스와 그 사이의 연관·의존(`-->`, `..>`, `*--`, `o--`)을 넣습니다. 10개 안팎. 인터페이스에 기대는 구조(의존 역전 등)를 보이려면 그 인터페이스의 구현 관계(`<|..`) 하나는 함께 둡니다.
- 두 목적이 다 필요하면 그림 둘로 나눕니다. 한 그림에 상속 몇 개와 참조 여러 개가 섞여 있으면 둘 중 무엇을 보이려는 그림인지 먼저 정합니다.

## 점검 포인트

- [ ] **시스템 구조 섹션**에 다이어그램이 최소 1개 있다 (필수)
- [ ] 다이어그램이 **요약**이다 — 핵심 구성요소만 (클래스 10개 이하 권장)
- [ ] 다이어그램 앞뒤에 **"이 그림에서 봐야 할 것"** 한 줄 설명이 있다
- [ ] **종류가 설명하는 것과 맞다** — 위 「소스에서 읽히는 것 → 다이어그램」과 「잘못 고른 그림을 알아보는 신호」로 판정. 안 맞으면 **권장**(그림마다 1건 — 상태 전이를 플로우차트로 그린 것은 아래 "상태 전이 그림이 있다"와 같은 건으로 셈)
      (예: 데이터 필드를 플로우차트로 · 여러 클래스의 호출 차례를 플로우차트로 · 상태 전이를 플로우차트로)
- [ ] 클래스 다이어그램이 **한 목적**이다 — 상속 구조 그림에 상속·구현 관계가 없는 클래스가 섞여 있으면 **권장**
- [ ] 상태 전이가 핵심인 기능(AI·보스·UI 흐름)에 상태 전이 그림이 있다 (권장)
- [ ] 설명은 있는데 맞는 그림이 없는 곳 — **참고**로 그 종류의 그림을 제안. 신호가 강한 곳만, **기능 단위마다 많아야 1건**:
      서로 이어지는 데이터가 둘 이상인데 글·표로만 설명 → ERD / 클래스 셋 이상을 차례로 부르는 흐름이 글·코드로만 → 시퀀스 / 상태 값을 바꾸는 코드가 있는데 그림이 없음 → 상태
- [ ] Mermaid 문법 오류가 없다 (상세 문서에서 렌더 실패 시 빨간 오류 박스가 뜸. 슬라이드는 같은 원문 블록을 그리므로 거기서도 깨짐)
- [ ] 슬라이드 장면에 들어갈 다이어그램이 **노드 10개 안팎 · 가로(`LR`) 방향**이다 — 아래 「슬라이드에서 작아지는 문제」 (참고)

## 슬라이드에서 작아지는 문제

슬라이드는 다이어그램을 1280×720 장면에 **통째로 맞춰** 그립니다. 세로로 길거나 노드가 많으면 그림 전체가 줄어들어
글자가 작아지고, 화면·PDF에서 읽히지 않습니다. 렌더러는 **실효 글자 크기**(글자 크기 × 표시 폭 ÷ 그림 원래 폭)가
**10px 미만**이면 참고 지표 `tiny-diagram`을 남깁니다(빨간 배지 아님, `PFScene.report().info.notes`).

| 증상 | 방향 (리포트에 적는 말) |
|---|---|
| 세로로 긴 `flowchart TD` | `flowchart LR`로 바꾸면 16:9 화면에 맞습니다 |
| 노드가 15개 넘는 클래스 그림 | 핵심 클래스 10개 안팎만 남기고, 나머지는 다른 그림으로 나누세요 |
| 참여자가 많고 긴 시퀀스 | "요청 → 검증"과 "판정 → 결과"처럼 **둘로 나누세요** |
| 노드 글자가 긴 문장 | 라벨은 짧게, 설명은 그림 바깥 한 줄 캡션으로 |

- 리포트 문구 예: "[참고] 슬라이드 7번째 장면(§3.2)의 다이어그램이 작아 보입니다(약 8px). 둘로 나누거나 가로(LR)로 바꿔 보세요."
- 고치는 곳은 `src/`의 프로젝트 문서입니다. 슬라이드는 원문 블록을 그대로 그리므로 원문을 고치면 상세 문서·슬라이드가 함께 바뀝니다.

## 빠진 다이어그램을 제안할 때 (프롬프트 틀)

리포트에는 **Mermaid 코드를 대신 써 넣지 말고**, 학생이 직접 AI에게 요청할 수 있는 프롬프트를 제안합니다.
학생이 코드를 받은 뒤 **읽고 고쳐서** 자기 문서에 넣는 것이 원칙입니다.

```text
다음 [무엇]을 Mermaid [다이어그램 종류]로 그려줘.
[구성요소·관계·순서를 목록으로 구체적으로 나열]
[특별히 강조할 표현 방식: 점선/마름모/PK·FK 등]
Mermaid 코드 블록으로만 답하고 설명은 빼줘.
```

- 문서·`code/` 어디에도 없는 이름(Animator에만 있는 전이 조건, 서버 코드에만 있는 메시지 이름 등)은 지어내지 않고 "(직접 채움: ○○에서 확인)"으로 비워 둡니다.
- 팀 프로젝트([팀])는 **내가 만든 부분**만 제안합니다. 팀원이 만든 데이터·클래스는 넣지 않거나 "팀원 파트"로 표시합니다.
- [구성요소]에는 코드·문서에 있는 **실제 이름**을 채웁니다: ERD는 데이터(클래스·표) 이름과 필드·타입, 이어 주는 `id` 필드 / 시퀀스는 참여자(클래스·서버·클라이언트)와 차례대로의 메서드·메시지 이름 / 상태는 `enum` 값과 전이 조건 / 클래스는 상속·구현 관계(또는 협력 관계) 하나만.
- 이름을 찾은 곳(`code/파일:줄`, 문서 §절)을 요청 문장 아래에 적어, 수강생이 받은 그림을 코드와 맞춰 볼 수 있게 합니다.
