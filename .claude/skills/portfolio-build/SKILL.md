# /portfolio-build — 포트폴리오 데이터 생성

대상: `$ARGUMENTS` (비어 있으면 `src/`의 모든 프로젝트, 폴더 이름이면 그 프로젝트만 다시 만듦)

시작 전에 `CLAUDE.md`의 **반드시 지킬 원칙**을 다시 확인합니다. 핵심은 **지어내지 않기**와 **수강생 문서를 고쳐 쓰지 않기**입니다.

## 0. 준비 — 기준 읽기

1. [schema.md](schema.md) — 출력 형식 (반드시 이 형식대로). 맨 아래 「슬라이드 `deck`」 절까지 끝까지 읽습니다
2. `format/01-portfolio.md` — 포트폴리오 페이지·슬라이드·상세 문서에 무엇이 들어가는지, 체크리스트
3. `format/02-tech-document.md` — 5단 구조 판정 기준
4. `format/03-diagrams.md` — 다이어그램 점검 기준
5. `format/04-layout-patterns.md` — 레이아웃 패턴 → 장면 틀. 슬라이드 장면마다 `layout`을 고를 때 참고(§2-2)
6. `profile.md`

## 1. 프로젝트 찾기

- `src/*/`에서 `_`로 시작하지 않는 폴더 = 프로젝트. 폴더 이름이 곧 `id`.
- 프로젝트 문서 = 폴더 바로 아래의 `.md` 파일 (`프로젝트문서.md` 우선, 그다음 예전 이름 `기술문서.md`, 없으면 `README.md`, 그것도 없으면 유일한 `.md`).
  하위 폴더 `_intake/`(`/portfolio-intake`가 만든 재료집·촬영목록·발표자료와 `pptx/` 그림)는 **프로젝트 문서가 아니므로 읽지 않습니다**. 루트 `.md`가 없고 `_intake/`만 있으면 그 프로젝트는 건너뛰고 리포트에 "아직 재료집 단계입니다 — `_intake/`의 재료집·발표자료 질문에 답해 `프로젝트문서.md`를 직접 쓴 뒤 다시 실행하세요"라고 적습니다.
  `.md`가 없으면 그 프로젝트는 건너뛰고 리포트에 "프로젝트 문서 없음"으로 적습니다.
  (리포트의 자리: `## 프로젝트별 점검` 끝의 `### 건너뛴 폴더`, 등급 없이 한 줄씩 — 요약 표 개수에 넣지 않음. 폴더 하나만 다시 만들 때도 적음.)
  건너뛴 프로젝트마다 "무엇을 더 준비하면 되는지는 `/portfolio-check <폴더>`의 **재료 점검표**로 볼 수 있습니다"를 덧붙입니다
  (뼈대 칸마다 필요한 자료는 `format/07-materials.md`). 빌드가 재료 점검표를 직접 만들지는 않습니다.
- `deck-edits.json`(장면 고치기 파일, `/portfolio-edit`가 씀)은 프로젝트 문서가 아닙니다. 빌드는 **읽기만** 하고(§2-2 key, §5 반영) 절대 쓰지 않습니다.
- `images/`의 실제 파일 목록, `code/`의 `.cs` 목록(하위 폴더 포함 `code/**/*.cs`)을 Glob으로 확보해 둡니다.

## 2. 프로젝트별 추출

프로젝트마다 프로젝트 문서를 **끝까지** 읽고 [schema.md](schema.md)의 `data/projects/<id>.json`을 채웁니다
(`schemaVersion: 2`, 포트폴리오 페이지용 필드 + 슬라이드 `deck`).
프로젝트가 3개 이상이면 **프로젝트마다 서브에이전트를 병렬로** 띄워도 됩니다
(각 에이전트에 `CLAUDE.md`·schema.md·format/01·02·03·04 경로와 이 단계·§4의 규칙을 넘김. profile.md는 필요 없음.
에이전트는 `data/projects/<id>.json`을 직접 쓰고 ① 문서 구성(뼈대 + 붙은 모듈, `format/02`) ② 점검 항목 ③ "확인해 주세요" 목록(슬라이드 글 조각은 장면별로 묶어서)
④ 기술 스택 근거 후보(`기술 | 근거 문장 | 원문 섹션`) ⑤ 스크린샷·링크·code/ 통계 ⑥ 슬라이드 장면 수를 돌려줌. portfolio.json·report.md는 부모가 씀).

### 2-1. 포트폴리오 페이지용 필드

- **원문에 있는 것만.** 문장은 압축해도 되지만 사실·수치·기술명을 더하지 않습니다.
- 무엇이 "그대로"이고 무엇이 "압축"인지는 [schema.md](schema.md)의 구분을 따릅니다. **압축한 필드**는 목록으로 기억해 두었다가 리포트 "확인해 주세요"에 넣습니다.
- `intent`(개발 의도): 개요에서 왜 만들었는지(무엇에 집중했는지)를 쓴 글에서 1~2문장. 원문 문장을 그대로 잘라 쓸 수 있으면 `verbatim: true`,
  줄이거나 합쳤으면 `verbatim: false`(→ "확인해 주세요"). 왜 만들었는지를 쓴 글이 없으면 `null`(그 자체는 format/02 기준으로 **필수** 항목이 됩니다).
- `highlights`: 문서의 **핵심 시스템/기능 섹션**에서 2~4개. `why`는 같은 기능의 "고민과 선택"에서 찾습니다.
  흩어져 있으면(기능 단위가 반복되는 문서) 해당 기능 근처의 선택 근거를 씁니다. 근거가 없으면 `""`.
  `image`: 그 기능의 `section` 절 안(표 밖)에 **실제로 있는** 이미지 하나(`src`·`w`·`h`·`caption`). 그 절에 이미지가 없으면 `null` — 다른 절의 그림을 가져오지 않습니다.
- `troubleshooting`: 문서의 문제 해결 사례(문제 → 원인 → 해결)에서 임팩트가 큰 순으로 최대 3개. 그 문제가 생긴 기능 장 안의 절이든 별도 장이든 같습니다.
- `retro`: 결론(회고) 장에서. 달성 = 목표한 경험이 어떻게 됐는지와 이룬 것, 아쉬운 점 → 계획 = 회고의 "겪은 일 → 다음에는"(schema.md).
- `screenshots`: `images/`에 **실제로 있는** 파일 중, 서로 다른 기능을 보여주는 최대 6장. 커버와 겹치지 않게.
- `retro.section`: 회고(결론) 장의 제목 글자 그대로(없으면 `""`).
- `section`: 원문 제목 텍스트를 **글자 그대로** 복사 (`### ` 같은 기호만 제외).
- `w`·`h`: 이미지 **파일 머리에서 읽은** 픽셀 크기만. 눈대중·문서에 적힌 숫자는 쓰지 않습니다. 한 줄 예(프로젝트 폴더의 `images/` 전체):
  - PowerShell: `Add-Type -AssemblyName System.Drawing; Get-ChildItem src\<id>\images\* | % { $i=[Drawing.Image]::FromFile($_.FullName); "$($_.Name) $($i.Width) $($i.Height)"; $i.Dispose() }`
  - 파이썬(Pillow가 있을 때): `python -c "import glob;from PIL import Image;[print(p,*Image.open(p).size) for p in glob.glob('src/<id>/images/*')]"`
  - 읽지 못한 파일(예: `.webp`)은 `w`·`h`를 **빼고** 둡니다(렌더러가 실행 중에 잼).
- 팀 프로젝트면 `team.role`을 반드시 찾습니다. 없으면 `""`로 두고 리포트 **필수** 항목.

### 2-2. 슬라이드 `deck` 만들기

[schema.md](schema.md) 「슬라이드 `deck`」 절의 형식과 규칙을 그대로 따릅니다. 순서:

1. **장 나누기** — 원문 `##`(H2) 순서대로 `chapters[]`. 목차 H2(`목차`·`차례`·`Contents`)는 빼고, 개요 앞의 요약 H2(예: `0. 한 장 요약`)는
   장으로 만들지 않습니다(표지·개요 재료로만). `title`은 번호·`★` 같은 기호만 뗀 글자, `sectionPath`는 그 H2 제목 그대로 한 칸.
   **회고(결론) 장** — `retro.section`이 가리키는 H2 — 도 `chapters[]`에 넣지 않습니다. 렌더러가 `retro`로 회고 장면을 따로 만들기 때문입니다
   (그 장 안의 표·그림은 상세 문서에 그대로 있습니다). AI 협업 장은 다른 장처럼 장으로 만듭니다.
2. **절마다 장면 틀 고르기** — 장 안의 절(H3·H4)을 위에서 아래로 보며 장면을 만듭니다. 절에 무엇이 있는지로 `layout`을 고릅니다
   (`format/04`의 패턴 → 장면 틀 대응도 참고):

   | 절에 있는 것 | `layout` | `tab` 예 |
   |---|---|---|
   | 개요(무엇을·왜)·개요 표 | `overview` | 개요 |
   | 플레이 소개(한 판의 흐름)·코어 루프 | 화면이 2~3장이면 `screens`, 흐름 그림(mermaid·이미지)이 있으면 `visual`, 규칙 표만 있으면 `full`, 글만이면 `overview` | 개요 · 흐름 |
   | 팀 구성과 내 역할·담당 파트 | `overview` (그 절이 역할 표 하나와 두세 줄 글뿐이면 `full`) | 개요 |
   | AI 협업(맡긴 것·직접 판단한 것·확인한 방법) | 표가 있으면 `full`, 글만이면 `overview` — 장면 하나 | `""` |
   | 다이어그램(mermaid) 또는 그림 + 설명 | `visual` | 구조 · 흐름 |
   | 코드 블록 + 설명 | `code` | 구현 |
   | 큰 다이어그램·비교 표·As-Is/To-Be 표 하나가 주인공 | `full` | 구조 · 선택 |
   | 스크린샷·GIF 2~3장 | `screens` | 결과 |
   | 문제 해결 사례(문제 → 원인 → 해결 → 결과) — 기능 장 안의 절이든 별도 장이든 | `problem` — 사례가 원문에 **표**로 있으면 그 표를 `visuals`에 그대로(`kind: "table"`, 근거 그림이 있으면 함께), `points`는 `[]`. 글로만 있으면 지금처럼 `points`(문제·원인·해결·결과·배운 점)로 옮기고 `verbatim: false`는 "확인해 주세요"로 | 문제 해결 |

   - 한 절에 구조 그림·흐름 그림·코드가 다 있으면 장면 셋(구조·흐름·구현)으로 **나눕니다**. "한 장에 한 항목"이 아니라 "한 장면에 한 메시지"입니다.
   - 장면 하나에 시각 자료는 1~2개. 시각 자료가 없는 절은 `overview`로 글(points 2~4)만 넣거나, 바로 위 장면의 `points`에 합칩니다.
     글만 있는 짧은 절이 이어지면 한 장면으로 묶습니다.
   - 절에 시각 자료가 없다고 **그 절과 무관한 그림·코드를 끌어오지 않습니다.** 그 절을 설명하는 데 쓰이는 상위·형제 절의 블록(예: 개요 장면의 대표 화면)은
     참조마다 자기 `sectionPath`를 적어 가리킬 수 있습니다.
3. **시각 자료는 블록 참조만** — `visuals[]`에는 `kind`·`n`·`fp`(이미지는 `src`·`w`·`h`·`caption`)만 적습니다. 다이어그램 코드·표 내용·소스코드를
   JSON에 옮겨 적지 않습니다(렌더러가 원문에서 그대로 그림).
   - `n`은 **그 절 범위**(제목부터 다음 제목 전까지, 하위 절 제외)에서 같은 `kind`끼리 1부터 셉니다. `mermaid` 펜스만 `mermaid`, 그 밖의 모든 펜스(언어 표시가 없어도)는 `code`.
   - `fp`(지문)는 원문에서 **복사**합니다: 코드·mermaid는 첫 비어 있지 않은 줄(60자까지, 글자 그대로. mermaid는 `%%`로 시작하는 지시 줄을 건너뜀), 표는 머리 칸을 `|`로 이은 것 —
     표 머리 칸은 렌더러가 그려진 글자로 비교하므로 굵게·기울임·백틱 기호(`*` `_` `` ` ``)와 링크 문법을 **뗀 글자**로 적습니다(예: `` `Tile`이나 `` → `Tile이나`).
   - 코드가 20줄을 넘으면 발표에 보일 핵심 부분을 `lines: [시작, 끝]`(펜스 제외, 1부터)로 지정합니다. 전체 코드는 상세 문서에 있습니다.
   - 같은 제목이 문서에 여러 번 나오면(예: `#### 개요`가 7곳) `sectionPath`에 위 제목을 **구분될 때까지** 앞에 붙입니다.
     그래서 절 제목마다 **Grep으로 그 글자가 몇 번 나오는지 먼저 셉니다**(코드 블록 안의 `#` 줄은 제목이 아님).
4. **글 조각에 `verbatim` 표시** — `title`은 절 제목 그대로(`verbatim: true`). `lead`·`points[].text`·`caption`은 경우가 둘뿐입니다:
   - 원문 그 절의 문장이나 표 칸을 **통째로** 옮겼으면 `true`(굵게·기울임·백틱 기호와 공백 차이만 허용). 원문 문장을 통째로 쓸 수 있고 장면 글자 수에 들어가면 이렇게 씁니다.
   - 그 밖에는 모두 `false` → 리포트 "확인해 주세요"에 **장면별로** 묶어 넣습니다. 문장의 앞이나 뒤를 떼어 낸 글도 여기입니다 — "그런데"·"그래서" 같은 접속어 하나,
     "…찾아본 뒤," 같은 앞 구절, 뒤의 덧붙임을 뗀 것은 남은 글자가 원문에 그대로 있어 §4 검사를 통과해도 `false`입니다. 줄이거나 합치거나 바꾼 글도 `false`.
   `points[].label`은 원문의 굵은 머리말·표 머리(첫 줄의 열 머리, 또는 첫 열의 행 머리 칸)에서 글자 그대로 가져오거나 schema의 라벨(`기능`·`구현`·`이유`·`문제`·`원인`·`해결`·`결과`·`배운 점`) 중 하나, 아니면 `""`.
5. **`key` 정하기** — 예전 `data/projects/<id>.json`이 있으면 **먼저 읽어**, `sectionPath`가 같은 장·장면은 예전 `key`를 그대로 씁니다
   (수강생이 공유한 `#s=d-<key>` 주소가 유지되게). 새 장면은 절 내용을 나타내는 짧은 영어 낱말(`^[a-z][a-z0-9-]{1,31}$`, `s-숫자`·숫자만은 금지)로 만들고,
   슬라이드 안에서 겹치지 않게 합니다.
   - 예전 data = 지금 디스크의 `data/projects/<id>.json`입니다. 커밋하지 않은 다시 빌드가 그 사이에 있었으면(`git status`에 그 파일이 바뀜으로 나옴) `git show HEAD:data/projects/<id>.json`의 key도 이어 받을 후보로 봅니다. 같은 key가 두 판에서 다른 절을 가리키면 HEAD 쪽을 따릅니다(배포된 공유 주소는 HEAD 쪽이므로).
   - 예전 data에 `deck.base`가 있으면 **그것이 예전 빌드 결과**입니다(`deck.slides`에는 장면 고치기가 반영되어 있음). key는 `deck.base`에서 이어 받고,
     `edited: true` 장면을 빌드 결과로 옮겨 적지 않습니다. `deck.base`·`deck.applied`·`edited`는 쓰지 않습니다(§5의 스크립트 몫).
   - 한 절에 장면이 여럿이면 예전 장면 중 시각 자료(kind·n·fp/src)가 가장 많이 겹치는 장면의 key를 이어 받습니다.
   - `src/<id>/deck-edits.json`이 있으면 읽어서 `pin[].key`·`hide`의 key를 **다른 절의 장면에 쓰지 않습니다.** 그리고 `pin[].from`·`hide[].from`이 가리키는 절에는
     **평소대로 장면을 만들고 같은 key를 씁니다**(그 절을 위 장면에 합치거나 빼지 않음). 스크립트가 그 빌드 장면을 찾아 고친 장면으로 바꿔 끼우거나 숨기므로,
     빌드가 그 장면을 만들지 않으면 고친 내용이 풀립니다(고아).
6. **분량** — 장면 수는 슬라이드에 **실제로 그려지는 장 수**(§7 미리보기의 `report().scenes`)이고, **15~30장**을 목표로 합니다.
   장면을 고르는 동안에는 식으로 어림합니다: `slides` 수 + 렌더러가 만드는 장면(표지·목차·맺음 3장 + 회고 1장(`retro`에 내용이 있을 때만) + 장 표지 = 장 수).
   렌더러는 장면 하나를 더 나누기도 합니다 — 20줄 넘는 코드(`d-<key>-2`…), 글자 하한에서도 안 들어가는 표(`d-<key>-t1`…), 한 장에 안 들어가는 회고(`retro-2`).
   그래서 쓴 뒤에 §7에서 잰 값으로 다시 봅니다. 코드·표가 나뉜 장은 장 수에 셉니다(빌드가 고른 `lines`와 표가 만든 장이므로).
   **회고가 나뉜 `retro-2`는 장면을 줄일 이유가 아닙니다** — 다 쓴 뒤 새 판을 30장과 견줄 때(아래 뺄 것, `tiny-diagram` 나누기)는 잰 값에서 `retro-2`를 빼고 셉니다.
   회고를 한 장에 맞추려고 `retro` 항목을 덜어 내지도 않습니다(회고 내용은 수강생의 것). 그래서 30장을 넘는 것이 `retro-2` 때문뿐이면 장면을 빼지 않고 `many-scenes` 참고만 적습니다(§7-1).
   (길 A·B를 가르는 이전 판의 장면 수는 이것과 따로, data만 보고 렌더러가 나눈 장을 모두 빼고 셉니다 — 아래 「장면이 많은 문서」.)
   30장을 넘으면 같은 절의 두 번째 코드 → 보조 표(개요 표가 아닌 표) → 겹치는 화면 순으로 뺍니다. 다만 **길 A(아래)의 이전 판 장면은 이 순서로 빼지 않습니다** —
   길 A에서 이 순서로 뺄 수 있는 것은 이번에 새로 더한 장면뿐이고, 이전 판 장면만으로 30장을 넘으면(이전 판에 코드·표가 나뉜 장면이 있으면 그럴 수 있음) 넘는 대로 두고 `many-scenes` 참고만 적습니다. 뺀 내용은 상세 문서에 그대로 있으니
   `points`로 다시 적어 보충하지 않습니다. 15장보다 적어도 억지로 늘리지 않습니다(짧은 문서는 짧은 슬라이드).
   - **장면이 많은 문서** — 아래 둘 중 하나이면 장면을 줄입니다:
     ⓐ 장이 많아(기능마다 장 하나) 고정 장면(표지·목차·맺음·회고 + 장 표지)만으로 15장을 넘을 때,
     ⓑ 장은 적어도 절이 많아, **시각 자료(이미지·GIF·다이어그램·코드·표)가 있는 절마다 1장 + 고정 장면**으로 센 수가 30장을 넘을 때.
     두 셈은 문서만 보고 하며, 누가 세어도 같은 수가 나오게 아래처럼 셉니다:
     - **고정 장면** = 3(표지·목차·맺음) + 회고 1(`retro`에 내용이 있을 때. 렌더러가 회고를 나눠도 1) + 장 수(§2-2 1의 장 — 목차·개요 앞 요약·회고 장은 장이 아님).
     - **절** = 장 첫머리(H2 바로 아래)와 H3·H4. H5 이하 제목 아래의 블록은 바로 위 H2~H4 절의 것으로 셉니다.
       **장이 되지 않는 H2는 그 아래 절까지 세지 않습니다** — 목차·개요 앞 요약·회고(결론) 장. 회고 장은 렌더러가 회고 장면으로 그리므로 고정 장면의 회고 1에 이미 들어 있습니다.
       첫 H2 앞(문서 제목·머리글)도 세지 않습니다.
     - 한 절을 장면 여럿으로 나누는 것, 빼는 순서, 렌더러가 장면을 나누는 것은 이 셈에 넣지 않습니다.
     - 리포트 「장면 고르기」 첫 줄에 센 수를 `절 N개 + 고정 M장`으로 적습니다(§6).
     이때도 30장을 맞추려고 **기능 장을 통째로 빼지 않습니다.** 줄이는 길은 **이전 판**에 따라 둘로 갈립니다.
     - **이전 판** = 마지막 커밋의 data(`git show HEAD:data/projects/<id>.json`, `deck.base`가 있으면 그것)입니다 — 배포된 공유 주소(`#s=d-<key>`)가 그 판에 있습니다.
       커밋하지 않은 다시 빌드 결과(디스크의 data)는 공유된 적이 없으니 기준이 아닙니다. 커밋된 판이 없으면 처음 빌드하는 문서로 봅니다.
     - **이전 판의 장면 수**(길 A·B를 가르는 값) = 이전 판의 `slides` 수 + 고정 장면(표지·목차·맺음 3 + 회고 1(`retro`에 내용이 있을 때) + 장 표지 = 이전 판 `chapters` 수)입니다.
       data만 보고 세며, 이전 판을 슬라이드로 열어 재지 않습니다. **렌더러가 나눈 장은 어느 것도 세지 않습니다** — 20줄 넘는 코드의 `d-<key>-2`…, 표의 `d-<key>-t1`…, 회고의 `retro-2`.
       그 장들은 한 장면이 길어서 나뉜 것이지 공유 주소가 있는 장면이 늘어난 것이 아니므로, 그 때문에 길 B로 넘어가 이전 판 주소를 잃지 않게 하기 위함입니다.
       예: 이전 판 `slides` 18개 + 고정 12장 = 30장이면, 그중 한 장면의 코드가 34줄이라 31장으로 그려지거나 회고가 길어 두 장으로 그려져도 30장으로 보고 길 A입니다.
     - **`highlights`가 장(H2)을 가리킬 때**(`section`이 장 제목) — 아래 길 A의 "더합니다"와 길 B의 ①에서 남길 장면은 **그 장의 대표 장면 하나**입니다:
       이전 판이 있으면 이전 판에서 그 장의 첫 장면(같은 절·같은 시각 자료·같은 key), 없으면 ④ 기준으로 고른 그 장의 장면 중 가장 앞에 오는 것.
       렌더러(`assets/common.js`의 `PF.deckSceneFor`)는 [슬라이드 열기]의 도착지를 ⓐ `sectionPath`의 **마지막**이 그 글자인 장면 → 없으면 ⓑ `sectionPath` 어디에든 그 글자가 든 장면 중 **슬라이드 순서로 첫 장면**으로 찾습니다
       (굵게·기울임·백틱 기호와 공백 차이만 무시, 앞부분 일치는 보지 않음). 그 장의 장면은 모두 `sectionPath` 맨 앞에 장 제목을 가지므로, 장 첫머리만 다룬 장면(`sectionPath`가 장 제목 하나)이 없으면 **그 장의 첫 장면**이 도착지입니다.
       그래서 대표 장면이 그 장의 첫 장면이 되게 둡니다(장 안의 장면은 원문 순서이므로, 대표 장면보다 앞 절의 장면을 새로 더하면 도착지가 바뀜 — 그럴 때는 대표 장면 앞에 더하지 않음).
     - **길 A — 이전 판이 30장 이하**: 공유했을 수 있는 주소를 지키는 것이 먼저입니다. **이전 판 장면을 모두 남깁니다**(같은 절의 장면을 같은 시각 자료(kind·n)와 같은 key로).
       장마다 장면 수를 이전 판이 그 장에 가진 수 아래로 깎지 않습니다(아래 자리 수 규칙을 쓰지 않음).
       - 빠지는 이전 장면은 **그 장면의 원문 블록이 문서에서 없어진 것뿐**입니다(그림 종류가 바뀌어 지문만 달라진 것은 없어진 것이 아님 — 새 지문으로 남김). 빠지면 리포트 「장면 고르기」에 `이전 판에서 뺌: d-<key>(§x) — 이유`를 적습니다.
       - `highlights`가 가리키는 절의 장면과 `deck-edits.json`의 `pin[].from`·`hide[].from`이 가리키는 장면(§2-2 5)이 이전 판에 없으면 더합니다.
       - 남는 자리(30 − 지금까지의 장면 수. 분량 식으로 세고 회고는 1장)가 있을 때만 새 장면을 더하고, 그 자리는 아래 ④ 내용 기준으로 고릅니다. 개요 장을 채우려고 쓰지 않습니다(개요 장은 이전 판에 있던 만큼).
       - 쏠림 막기(아래)도 그대로 적용합니다. 더해서 30장을 넘으면 넘는 대로 두고 참고(`many-scenes`)에 적습니다.
       - 다 쓴 뒤 §7에서 잰 장 수가(`retro-2`를 빼고도) 30장을 넘어도 **이전 판 장면은 빼지 않습니다**. 이전 판에 20줄 넘는 코드·큰 표 장면이 있으면 길 A인데도 31장 이상으로 재질 수 있습니다(렌더러가 나눈 `d-<key>-2`·`-t1` 장은 그 이전 판 장면의 일부입니다) — 넘는 대로 두고 `many-scenes` 참고만 적습니다.
     - **길 B — 이전 판이 30장을 넘거나, 처음 빌드하는 문서**: 장마다 장면 자리를 정해 줄입니다.
       - **자리 수**: 짧은 장(하위 절(H3)이 2개 이하이거나 시각 자료가 1개 이하)과 **개요 장**은 1개, 나머지는 2개가 기본입니다.
         기본 자리를 다 채워도 30장에 못 미치면(ⓑ에서 흔함), 남는 자리(30 − 고정 장면 − 기본 자리 합)를 하위 절이 많은 기능 장부터 한 자리씩 돌아가며 더 줍니다(한 장에 4개까지. 짧은 장·개요 장에는 주지 않음).
       - **남기는 순서** — 장마다 자리를 아래 순서로 채웁니다:
         ① `highlights`가 가리키는 절의 장면(절 하나에 대표 장면 하나. 이것만으로 자리 수를 넘으면 모두 남김 — 포트폴리오 페이지의 [슬라이드 열기]가 이 장면으로 감)
         ② `src/<id>/deck-edits.json`의 `pin[].from`·`hide[].from`이 가리키는 장면(§2-2 5 — 빌드가 만들지 않으면 고친 내용이 풀림. 자리 수를 넘어도 남김)
         ③ **이전 판에 있던 장면**(주소 보존) — 같은 절의 장면을 같은 시각 자료(kind·n)로 만들어 남깁니다. **남은 자리 안에서만** 채웁니다:
            이전 판이 자리보다 많은 장면을 가졌으면(예: 장 하나에 4장면인데 자리가 3개) 다 남기지 않고, 그 장의 요점을 더 잘 싣는 장면을 ④의 기준으로 골라 남깁니다. 처음 빌드하는 문서는 ③을 건너뜁니다.
         ④ 남은 자리 — 아래 내용 기준으로 고릅니다.
     - (길 B) 문제 해결 사례(`troubleshooting`이 가리키는 절 포함)는 ①처럼 먼저 남기지 않고 다른 블록과 같이 ④ 기준으로 고릅니다(포트폴리오 페이지의 이슈 해결 사례 데이터는 그대로).
     ④의 자리는 **고정 순위가 아니라 내용으로** 고릅니다. 장마다 "이 장에서 수강생이 말하려는 것"(장 첫머리·절 제목·고민과 선택의 결론)을 먼저 한 줄로 정하고,
     그것을 가장 잘 실어 나르는 절과 블록을 고릅니다:

     | 그 절의 요점이 | 실어 나르는 블록 |
     |---|---|
     | 판단 — 왜 이 방법인가(대안 비교) | 비교 표 (`full`) |
     | 동작·느낌 — 플레이에서 어떻게 보이나 | 화면·GIF (`visual`·`screens`) |
     | 관계·흐름 — 무엇이 무엇을 부르나, 어떤 순서인가 | 다이어그램 (`visual`·`full`) |
     | 구현 방식 — 어떻게 짰나 | 코드 (`code`) |
     | 겪은 문제 — 무엇이 왜 잘못됐고 어떻게 고쳤나 | 문제 해결 (`problem`) |

     - 같은 요점을 두 블록이 실으면, 원문이 그 절에서 더 많이 설명하는 쪽(그 블록을 가리키며 쓴 글이 긴 쪽)을 고릅니다.
     - **쏠림 막기**: 고르고 나서 슬라이드 전체를 훑어, 빌드 장면의 절반 넘게가 한 종류(비교 표·코드·다이어그램·화면 중 하나)이면 그 종류가 아니어도 요점이 서는 장부터 다른 블록으로 바꿉니다.
       원문에 화면(이미지·GIF)이 있는데 슬라이드에 화면 장면이 하나도 없거나, 문서에 고민과 선택이 있는데 비교 표 장면이 하나도 없거나, 문서에 문제 해결 사례가 있는데 문제 해결 장면(`problem`)이 하나도 없으면, 그 종류의 장면을 **하나 더합니다**(그 장의 다른 블록을 빼지 않음 — 그 장의 자리 수를 넘어도 됨). ①~③으로 남긴 장면 뒤에도 똑같이 적용합니다. 더하는 것은 종류마다 하나뿐입니다.
       살릴 문제 해결 사례는 `troubleshooting`이 가리키는 사례 중에서 그 장의 요점에 가장 가까운 것으로 고릅니다(슬라이드 옛 주소 `ts-n`이 그 장면으로 열리게). 이것은 "0개는 안 된다"만 정하는 것이고 순위가 아닙니다.
     - 고른 이유는 리포트 `## 장면 점검`의 그 슬라이드 아래 「장면 고르기」에 **장마다 한 줄**로 남깁니다(§6). 판단이라 실행마다 달라질 수 있으므로, 수강생이 보고 `/portfolio-edit`로 바꿀 수 있게 하기 위함입니다.
     고른 뒤 §7 미리보기에서 `tiny-diagram`(다른 자료와 한 장면 — 나누면 커짐, 실효 글자 10px 미만)이 나온 장면은, 나눈 뒤에도 그 장의 장면이 자리 수 이하이면(길 A는 슬라이드 전체가 `retro-2`를 빼고 30장 이하이면) 다이어그램을 따로 장면으로 나눠 다시 확인합니다(자리 수를 넘게 되면 나누지 않고 참고로 둠).
     예외: `highlights`가 가리키는 장면(포트폴리오 페이지 [슬라이드 열기]의 도착지)은 그 장이 자리 수를 넘어도 나눠 봅니다. 나눈 뒤 다시 잰 다이어그램이 **10px 이상이 될 때만** 나눈 채로 두고,
     여전히 10px 미만이면(대개 세로·가로로 긴 그림이라 높이·폭에 막힘) 나누지 않은 상태로 되돌린 뒤 리포트 장면 점검에 "이 그림은 문서에서 둘로 나눠야 커집니다"라고 적습니다. 하이라이트가 아닌 장면에는 넓히지 않습니다.
     그래도 30장을 넘으면(`retro-2`를 빼고 셈) **넘는 대로 두고** 리포트 참고(`many-scenes`)에 장 수와 고정 장면 수를 적습니다 — 줄이는 방법은 슬라이드가 아니라 문서에 있습니다
     (`format/02` 뼈대: 대안이 있었던 기능 2~4개만 깊게 쓰고 나머지는 표 한 줄).

**원문에 없는 내용 금지**는 슬라이드에도 그대로입니다. 설명·수치·장면 제목·라벨을 새로 만들지 않습니다.

### 2-3. 슬라이드 추가 모드

기존 `data/projects/<id>.json`이 있고 사용자가 **슬라이드만** 원하면(예: "슬라이드만 만들어 줘", "기존 데이터는 그대로 두고"):

- 기존 필드의 값은 **한 글자도 바꾸지 않습니다**(키 순서·들여쓰기도 그대로 두는 것이 가장 안전). 압축 문장을 다시 만들지 않습니다.
- `schemaVersion`·`deck`·`intent`·`highlights[].image`·`retro.section`·`w`/`h`만 **더합니다**(§2-1·§2-2 규칙 그대로).

- §4의 "슬라이드 추가 모드" 항목으로 기존 값이 그대로인지 확인한 뒤 씁니다.

## 3. 프로필·기술 스택

- `profile`·`settings`는 `profile.md`에서만. 자기소개는 줄바꿈까지 그대로.
- `profile.md` 값이 예시 그대로(홍길동, you@example.com, your-id)면 그대로 싣되 리포트 **필수**에 "예시 값을 바꾸세요".
- `skills`: profile.md 기술 스택 메모의 기술마다 프로젝트 문서에서 근거를 찾아 `evidence`를 만듭니다.
  메모가 비어 있으면 여러 프로젝트에 공통으로 등장하는 기술 위주로 3~8개 고릅니다.
  **근거를 못 찾은 기술은 빼고** 리포트에 알립니다.
- `projects`: profile.md `프로젝트 순서` → 없으면 폴더 이름 순. 순서에 적힌 이름은 실제 `src/` 폴더 이름과 **대소문자까지** 맞춰 보고,
  맞는 폴더가 없는 이름은 싣지 않고 리포트 **필수**에 적습니다.
- §1에서 건너뛴 프로젝트(프로젝트 문서 없음·재료집 단계)는 `projects`에 넣지 않습니다(`profile.md` `프로젝트 순서`에 적혀 있어도 — 그 이름은 리포트에 "문서 없음"으로만 적고 필수로 세지 않음).
- 폴더 이름 하나만 다시 만드는 경우: 그 프로젝트 JSON만 다시 쓰고, `portfolio.json`은 `skills`의 해당 프로젝트 근거와 `projects` 목록, `generatedAt`(오늘 날짜)만 갱신합니다.
  `projects`는 예전 목록을 유지하고 이번 프로젝트가 없으면 위 순서 규칙의 자리에 더합니다. `data/projects/<id>.json`이 없는 폴더(아직 빌드하지 않은 폴더)는 넣지 않고 리포트 `## 프로필`에 "전체 `/portfolio-build`를 실행하면 실립니다"라고 적습니다.

  스크린샷 칸은 "프로젝트 문서 안 이미지 수 / 4~6"(예: `7 / 4~6`)입니다. 4장보다 적으면 권장, 6장을 넘는 것은 지적하지 않습니다.
- `## 확인해 주세요`의 슬라이드 글 조각(`verbatim: false`인 `lead`·`points`·`caption`·줄인 `title`)은 **장면마다 한 줄**로 묶어 적습니다
  (`[프로젝트 · 슬라이드 d-<key> (§절)] 도입 "…" · 요점(라벨) "…"`). 장면이 많아도 한 줄씩이라 수강생이 장면 순서대로 훑어볼 수 있습니다.
  고친 장면(`edited: true`)의 줄은 §5 스크립트 출력을 글자 그대로 옮깁니다(이미 `[프로젝트 · 슬라이드 d-<key> (§절) · 고친 장면] …` 형식).
- 빌드가 **다른 절의 원문 블록**(참조에 자기 `sectionPath`가 있는 시각 자료)을 장면에 넣었으면 같은 줄에 `다른 절의 그림: §x`(다이어그램·표·코드도 그 이름으로)를 덧붙입니다
  (그 장면에 `verbatim: false` 글 조각이 없어 줄이 없으면 `[프로젝트 · 슬라이드 d-<key> (§절)] 다른 절의 그림: §x` 줄을 새로 만듭니다)
  — 장면과 그림의 절이 다르다는 것을 수강생이 알도록(결정 I6).
- 장면이 많은 문서 규칙(§2-2 6)으로 장면을 줄였으면, `## 장면 점검`의 그 슬라이드 아래 맨 끝에 「장면 고르기」를 둡니다 — 등급 없이, 개수에 넣지 않음.
  첫 줄에 걸린 조건과 길을 적고(길 A: `- 조건 ⓑ(시각 자료가 있는 절 39개 + 고정 12장 = 51장) · 길 A(이전 판 30장 모두 남김) — 새 장면 0개`, 길 B: `- 조건 ⓑ(…) · 길 B(이전 판 34장) — 고정 12장 · 자리 18개(§2 4 · §3 3 · …)`), 이어서 장마다 한 줄:
  `- §7 칸 효과(요점: 효과를 칸 밖으로 뺀 판단) — §7.3 비교 표(판단)·§7.2 다이어그램(흐름) 남김, §7.1 표 뺌 → 바꾸려면 /portfolio-edit`
  이전 판에서 이어 남긴 장면은 `(이전 판)`을, 새로 더한 장면은 `(새 장면)`을 붙입니다. 이전 판에 있었는데 뺀 장면(길 A는 원문 블록이 없어진 것, 길 B는 자리가 모자란 것)은 그 장 줄 끝에 `이전 판에서 뺌: d-<key>(§x) — 이유`로 적습니다(공유한 그 주소는 더 이상 그 장면으로 열리지 않음).
  (장은 `§번호 장 제목`으로 적습니다. "N장"은 이 리포트에서 장면 번호로 쓰므로 장에는 쓰지 않습니다).
- `## 장면 점검`은 §7에서 읽은 `audit`(필수)과 `info.notes`(참고)를 **장면마다 1건**으로 적습니다. 장면은 `9장 d-spawn-weight(§4.3)`처럼 번호·장면 id·절로 가리키고,
  "무엇이 얼마나(숫자) → 어떻게 하면 좋을지"를 쉬운 말로 씁니다. 장면 수는 슬라이드 머리에 함께 적습니다.

빠진 다이어그램을 제안할 때는 `format/03-diagrams.md`의 프롬프트 틀을 채운 **요청 문장**을 제안합니다 (Mermaid 코드를 대신 쓰지 않음).

## 7. 미리보기와 마무리 보고

1. 로컬 서버를 백그라운드로 띄웁니다: `python -m http.server 4600` (실패하면 `py -m http.server 4600`).
   이미 떠 있으면 재사용. 브라우저 도구가 있으면 세 페이지를 열어 콘솔 오류·깨진 이미지가 없는지 확인합니다.
   브라우저 도구가 없으면 `CLAUDE.md` 「미리보기」의 headless Chrome 방법(`?pf-audit=1`)으로 같은 `report()` JSON을 읽고 `ready`가 `yes`인지 확인합니다.
   상세 문서도 같습니다(`doc.html?p=<id>&pf-audit=1` — 그림까지 받은 뒤 씀. 상세 문서의 `ready`는 `true`).

   **7-1. 프로젝트마다 슬라이드(`project.html?p=<id>`)**
   — `await PFScene.whenReady()` 뒤 `PFScene.report()`를 읽습니다.

   - **장면 id**: 슬라이드 = `cover` · `toc`(목차) · `ch-<장 key>`(장 표지) · `d-<장면 key>`(코드로 나뉜 장면은 `d-<key>-2`…, 표로 나뉘면 `d-<key>-t1`…) ·
     `retro`(회고, 두 장이면 `retro-2`) · `end`(맺음). `key`가 규칙에 어긋나거나 겹치면 렌더러가 `d<장 번호>-<순번>`으로 바꿉니다(→ `key-invalid`). `audit` 항목의 장면 이름은 `report().ids[scene - 1]`, `info.notes[]` 항목은 `id`를 바로 갖습니다.
     슬라이드는 표지를 포함해 모든 장면이 그 프로젝트의 `data/projects/<id>.json`과 src/ 프로젝트 문서에서 옵니다.
   - **`audit[]` — 빨간 배지와 장면 안 띠(배포된 페이지와 PDF에도 보임) → 리포트 필수.** 요소마다 한 줄이라 넘친 장면 하나가 여러 줄로 나오므로
     **장면(`scene` 번호)마다 1건**으로 묶습니다.
     - `clipped`(내용이 잘렸습니다): 그 장면에서 줄여야 할 원천을 적습니다 — `lead`·`points` 수·`visuals` 수(또는 장면을 둘로 나누기).
       표지(`cover`)가 잘리면 제목·한 줄 소개·역할·개발 의도가 원천입니다. 같은 장면의 `body-scroll`·`outside`(audit)와 `font-floor`(`info.notes`)는 같은 문제로 봅니다.
       원천이 **빌드가 고른 값**(`lines` 범위, `lead`·`points` 수와 길이, `visuals` 수, 장면 나누기)이면 빌드가 먼저 줄이거나 나눠 다시 확인합니다(수강생이 고칠 소스가 아니므로).
       원문 블록 하나가 그 자체로 커서(줄일 수 없는 표·그림) 남는 잘림만 **필수**로 적고, 방향은 프로젝트 문서 쪽(표를 둘로 나누기 등)으로 씁니다.
     - `visual-missing`(원문 블록 0곳) · `visual-ambiguous`(2곳 이상) · `visual-changed`(지문 불일치) · `key-invalid`(key 규칙 위반 또는 슬라이드 안 중복):
       **데이터(`deck`)가 틀린 것**이므로 §4대로 `sectionPath`·`n`·`fp`·`key`를 고쳐 다시 쓰고 **다시 확인**합니다. 리포트를 쓸 때는 0건이어야 합니다.
       끝내 0이 되지 않으면(예: 원문에 구분할 수 없는 똑같은 절이 둘) 그 장면을 **필수**로 적고 왜 못 풀었는지 씁니다(수강생이 원문 제목을 다르게 하면 풀림).
       예외: **고친 장면**(`deck.slides[].edited: true`, 띠 문구 "고친 장면입니다. /portfolio-edit로 고치세요")의 `visual-*`는 수강생의 고치기 파일이 원문과 어긋난 것이라
       빌드가 고치지 않습니다 → **필수**로 적고 "`/portfolio-edit <폴더> <장면>`으로 그림 참조를 다시 고르거나 되돌리세요".
       예외: `visual-missing`의 `detail`이 "다이어그램을 그리지 못했습니다"이면 블록은 찾았지만 **원문 mermaid 문법 오류**로 그리지 못한 것입니다(상세 문서 콘솔의
       `[doc] Mermaid 렌더 오류`와 같은 원인). 데이터가 아니라 원문 문제이므로 그 장면을 **필수**로 적고 "§n 다이어그램 문법을 고쳐 주세요"라고 방향만 씁니다.
     - `clipped`가 없는 장면의 다른 항목(`head-overlap`·`outside`·`inner-scroll`·`img-broken` 등)도 장면마다 1건.
     - `scene`이 null인 항목(`outside-deck`·`foreign`·`dialog`)은 src/로 고칠 수 없는 렌더러 문제이므로 리포트에 넣지 말고 마무리 보고에서 따로 알립니다.
   - **`info.notes[]` — 참고 지표(빨간 배지 없음) → 리포트 참고.** 항목은 `{scene, id, type, value, detail}`. 장면마다 1건, 쉬운 말로
     "무엇이 얼마나 → 어떻게 하면 좋을지":

     | `type` | 뜻 | 리포트 문구 예 |
     |---|---|---|
     | `low-fill` | 채움률 60% 미만(`value` = 채움률). `detail` 끝 괄호 = 장면에 든 것(`글만`·`표`·`코드`·`그림`·`다이어그램`) | 든 것에 따라 방향이 다릅니다(아래 「원인별 안내」). 예: "[참고] 슬라이드 12번째 장면 `d-input`(§5.1)은 글만 있어 장면의 약 45%만 채웠습니다. 그 절을 보여 줄 그림·표가 원문에 있으면 프로젝트 문서에 넣고 다시 빌드하고, 없으면 `/portfolio-edit`로 옆 장면과 합칠 수 있습니다" |
     | `tiny-diagram` | 다이어그램 실효 글자 10px 미만(`value` = px). `detail` 괄호 = 원인(`세로로 긴 그림 — 높이에 막힘` / `가로로 긴 그림 — 폭에 막힘` / `다른 자료와 한 장면 — 나누면 커짐`)과 다이어그램 원래 크기 | 막힌 쪽에 따라 방향이 반대입니다(아래). 예: "[참고] 슬라이드 7번째 장면 `d-arch`(§3.2)의 다이어그램 글자가 약 8px로 작습니다. 위아래로 길어서 장면 높이에 맞춰 줄었습니다 → 프로젝트 문서에서 단계별로 둘로 나누거나, 갈래가 적으면 LR 방향으로" |
     | `long-code` | 코드 20줄 초과로 "계속" 장면으로 나뉨(`value` = 줄 수) | "[참고] 슬라이드 9번째 장면 `d-pick`(§4.3)의 코드가 34줄이라 두 장면으로 나뉘었습니다. `/portfolio-edit`로 발표에 꼭 보일 줄 범위만 남길 수 있습니다(전체 코드는 상세 문서에 그대로)" |
     | `many-scenes` | 장면 30장 초과(`value` = 장면 수) | "[참고] 슬라이드가 34장입니다(권장 15~30). 같은 절의 두 번째 코드·보조 표·겹치는 화면 중 뺄 것이 있는지 봐 주세요". 장이 많아서 넘은 것이면 "[참고] 슬라이드가 43장입니다(권장 15~30). 장이 14개라 장 표지와 표지·목차·맺음·회고만 17장입니다 → 프로젝트 문서에서 깊게 다룰 기능을 2~4개로 고르고 나머지를 표로 묶으면 줄어듭니다". 장은 적은데 절이 많아 넘은 것이면 "[참고] 슬라이드가 33장입니다(권장 15~30). 장 7개에 절이 45개라 장마다 장면을 3~4개로 줄였습니다 → 깊게 쓴 절 중 비슷한 것을 한 절로 묶거나 표 한 줄로 줄이면 줄어듭니다". `retro-2`를 빼면 30장 이하이면(회고가 두 장으로 나뉨) "[참고] 슬라이드가 31장입니다(권장 15~30). 회고가 길어 두 장으로 나뉜 것이라 장면은 줄이지 않았습니다" |
     | `font-floor` | 글자 하한(본문 14 · 코드 12 · 라벨 11px)에 걸려 더 줄이지 못함 | `clipped`와 함께면 같은 건으로 묶음. 홀로면 "[참고] … 글자가 하한까지 작아졌습니다. 글을 조금 줄이면 글자가 커집니다" |
     | `auto-mode` | 예전 데이터로 자동 구성(`deck` 없음) | 그 슬라이드의 다른 notes는 적지 않고 **권장 1건**만: "[권장] 예전 데이터로 자동 구성된 슬라이드입니다. `/portfolio-build <폴더>`를 다시 실행하면 슬라이드가 됩니다" |

   - **원인별 안내**(참고 지표는 렌더러가 이미 가장 크게 보이는 배치를 고른 결과입니다. 장면 틀만 바꿔서 나아지지 않는 경우를 고치기로 안내하지 않습니다):

     | 지표 · 원인 | 방향 | `/portfolio-edit`로 되나 |
     |---|---|---|
     | `tiny-diagram` · 세로로 긴 그림(높이에 막힘, 시퀀스·위→아래 흐름도) | 프로젝트 문서에서 단계별로 둘로 나누기, 갈래가 적으면 LR 방향 | **안 됨** — 틀을 `full`로 바꾸면 오히려 더 작아짐 |
     | `tiny-diagram` · 가로로 긴 그림(폭에 막힘, 왼쪽→오른쪽 흐름) | 프로젝트 문서에서 TD(위→아래) 방향으로 바꾸거나 둘로 나누기 | 안 됨(이미 폭을 다 씀) |
     | `tiny-diagram` · 다른 자료와 한 장면(`다른 자료와 한 장면 — 나누면 커짐`) | 그 다이어그램만 따로 장면으로. 다만 괄호의 원래 크기가 세로·가로로 길면(예: 852×1216) 나눠도 높이·폭에 막혀 거의 커지지 않음 → 그때는 위 세로·가로형과 같은 방향(문서에서 나누기) | **됨** — 나누기(원래 크기가 긴 그림이면 효과 적음) |
     | `low-fill` · 글만 | 그 절을 보여 줄 그림·표가 원문에 있으면 프로젝트 문서에 넣고 다시 빌드 | 옆 장면과 **합치기** |
     | `low-fill` · 표 또는 코드만 | 표·코드는 원래 크기보다 커지지 않습니다(글자 하한·읽기 크기). 그대로 두어도 됨 | 옆 장면과 **합치기** |
     | `low-fill` · 다이어그램(가로로 긴) | 위 `tiny-diagram` 가로형과 같음 | 안 됨 |
     | `low-fill` · 그림 | 원본 이미지가 작으면 더 크게 다시 찍기(그림은 원래 크기의 1.25배까지만 키움) | 같은 절의 다른 그림과 **합치기** |

   - **어디에 적나**: 슬라이드의 모든 장면은 `## 장면 점검`의 그 프로젝트 아래에 적고 `## 요약` 표에서 그 프로젝트 행의 필수·권장·참고 개수에 더합니다.
   - 슬라이드에 쓰인 이미지 파일이 5MB를 넘으면(큰 GIF 등) **참고**로 적습니다: "`images/boss.gif`(12MB)는 느린 연결에서 슬라이드 준비가 오래 걸립니다.
     짧게 자르거나 크기를 줄이는 것을 생각해 보세요".

   **7-2. 프로젝트마다 프로젝트 상세 문서(`doc.html?p=<id>`)**
   - 프로젝트 문서 안의 이미지가 모두 보이는지(깨진 이미지는 슬라이드에서도 깨짐), 머리의 [슬라이드 ↗]가 그 프로젝트의 `project.html?p=<id>`로 가는지 확인합니다.
   - 콘솔 경고 `[doc] Mermaid 렌더 오류`가 보이면 원문 다이어그램 문법 문제입니다(7-1의 예외와 같은 원인 — 리포트 **필수**, 방향만).
   - `section` 값이 원문 제목과 다른 것은 이제 콘솔 경고로 알 수 없습니다(상세 문서 칩이 없어짐). §4의 `section` Grep 검증과 "`highlights[].section`이
     `deck.slides[].sectionPath`에 있다" 항목이 최종입니다 — 맞지 않으면 포트폴리오 페이지 기능 소개의 [슬라이드 열기]가 장면이 아니라 슬라이드 맨 앞으로 갑니다.

   **7-3. 포트폴리오 페이지(`http://localhost:4600/`)**
   — 장면이 아니라 아래로 읽는 한 페이지라 잘림 띠·장면 점검 지표가 없습니다. `await PFPage.whenReady()` 뒤 `PFPage.report()`를 읽습니다
   (브라우저 도구가 없으면 `index.html?pf-audit=1`의 `#pf-audit`, 형식은 7-1과 같음).
   - `sections`에 `portfolio.json`의 프로젝트마다 `p-<폴더>`·`p-<폴더>-core`(기능이 있을 때)가 있어야 합니다. 빠졌으면 그 프로젝트 JSON을 읽지 못한 것 → §4의 이름(대소문자) 검증으로 돌아감.
   - `images.broken`(열리지 않은 그림) → **필수**. 대표 이미지(`cover`)·기능 화면(`highlights[].image`) 경로와 실제 파일 이름(대소문자)을 맞춥니다. 그 프로젝트의 `## 장면 점검`에
     「포트폴리오 페이지」 항목으로 적고 요약 표 개수에 더합니다.
   - `deckLinks`(기능마다 [슬라이드 열기] 주소)에 `#s=`가 없는 것은 `highlights[].section`이 슬라이드 장면을 찾지 못한 것 → §4 검증으로 고쳐 다시 씀(장면 고치기로 그 장이 비어 §5 스크립트가 [권장]으로 알린 경우는 같은 건이므로 `section`을 고치지 않음).
   - `overflowX`가 0보다 크거나 `errors`가 있으면 src/로 고칠 수 없는 렌더러 문제이므로 리포트에 넣지 말고 마무리 보고에서 따로 알립니다.
   - `strings.issues`(문구 표 `theme/strings.tsv` 점검)가 있으면 리포트에 넣지 말고 마무리 보고에서 줄 번호(`line`)와 `detail`을 짧게 알립니다. 표는 수강생이 직접 고치는 파일입니다(CLAUDE.md 원칙 5).
   - 인쇄(A4, 제출 PDF)는 프로젝트마다 소개 1쪽 + 기능 소개 1쪽으로 나뉩니다. 리포트 항목은 아니며, 수강생이 [PDF로 저장]으로 직접 확인합니다.
